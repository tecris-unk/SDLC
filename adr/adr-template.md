# Записи архитектурных решений (ADR — Architectural Decision Records)

## ADR-001: Выбор C# (.NET 8) и ASP.NET Core Web API для серверной части

* **Статус**: Принято (Accepted)
* **Контекст**: Необходимо разработать надёжный, строго типизированный и высокопроизводительный backend для веб-приложения «TourGuide», обеспечивающий время отклика API при расчёте маршрутов и фильтрации каталога не более 2 секунд (`REQ-PERF-001`) и встроенную систему безопасности (`REQ-SEC-001`).
* **Решение**: Использовать платформу **.NET 8 (C#)**, фреймворк **ASP.NET Core Web API** и ORM **Entity Framework Core**.
* **Обоснование и последствия**:
  - Высокая производительность асинхронного конвейера обработки запросов (`async/await`, Kestrel) гарантирует выполнение `REQ-PERF-001`.
  - Наличие готового модуля `ASP.NET Core Identity` с поддержкой JWT ускоряет реализацию `REQ-SEC-001`.
  - Удобная работа со схемой БД через миграции `Entity Framework Core`.

## ADR-002: Выбор PostgreSQL в качестве основной СУБД и Docker для контейнеризации

* **Статус**: Принято (Accepted)
* **Контекст**: Приложение хранит структурированные данные о достопримечательностях, пользователях и упорядоченных точках экскурсионных маршрутов, а также должно запускаться в едином окружении на любой хост-системе (`REQ-PORT-001`).
* **Решение**: Использовать реляционную СУБД **PostgreSQL 16** (с провайдером `Npgsql.EntityFrameworkCore.PostgreSQL`) и упаковать приложение в контейнеры **Docker** (`docker-compose`).
* **Обоснование и последствия**:
  - PostgreSQL обеспечивает строгую целостность связей между маршрутами и точками (`ExcursionRoute` -> `RoutePoint` -> `Place`) и быструю индексацию при фильтрации.
  - Docker устраняет проблему несовместимости окружений при развёртывании на VPS и проверке работы.

## ADR-003: Упрощение конструктора маршрутов в MVP и интеграция OpenStreetMap + Leaflet

* **Статус**: Принято по итогам 1-го раунда согласования с Заказчиком (Accepted)
* **Контекст**: Полная реализация алгоритма автоматической оптимизации графа обхода точек (`REQ-FUNC-003`) и панели администрирования (`REQ-FUNC-006`) создавала риск срыва дедлайна первого релиза.
* **Решение**:
  1. Для отображения карты и маршрутов использовать открытую связку **OpenStreetMap + Leaflet** без платных лимитов.
  2. В рамках MVP реализовать ручное формирование порядка точек экскурсии пользователем, а автоматическую оптимизацию и админ-панель (`REQ-FUNC-006`) вынести на пост-релизный этап, заполнив начальную БД миграцией (Seed Data).
* **Обоснование и последствия**: Сокращение трудозатрат на 2 недели и сохранение фокуса на ключевой ценности продукта в Спринтах 1–3.

## ADR-004: Интеграция АИ-агента рекомендаций мест и расширение команды

* **Статус**: Принято по итогам 2-го раунда согласования с Заказчиком (Accepted)
* **Контекст**: Во втором раунде Заказчик запросил включение новой функции `REQ-FUNC-007` («АИ-агент рекомендаций мест по текстовому запросу и радиусу») без сдвига финального дедлайна релиза.
* **Решение**:
  1. Реализовать на стороне ASP.NET Core изолированный сервис `AiAgentService`, который передаёт пользовательский запрос и список доступных локаций в LLM API и возвращает отфильтрованные карточки из каталога PostgreSQL (с fallback-режимом стандартной фильтрации при недоступности внешнего сервиса).
  2. Привлечь в команду junior-разработчика на вёрстку React-компонентов (увеличение сметы на 2 000 BYN, итоговый бюджет — 15 000 BYN).
* **Обоснование и последствия**: Сохранение исходного срока релиза (4 спринта / 7,5 недель) при реализации интеллектуального подбора экскурсий.
